# Brands (A106)

## Brand attachments

Catalog → Brands → Attachments accepts public brand documents such as size guides. The shared uploader also serves Products → Attachments: drag/drop or choose files, edit saved display names, reorder, replace and remove, then save through the existing editor action. Pending files are uploaded on Save; removing a pending upload also reindexes replacement references. Product buyer downloads remain digital-only and separate from public attachments.

The additive `2026_11_29_000100_create_brand_files` migration links ordered, uniquely associated brand documents to the existing private file records. It adds foreign keys, positive-position/nonblank-name checks and the reviewed audit trigger. Uploads reuse the existing MIME/extension/size validation and cleanup lifecycle; cleanup retains files referenced by either a brand or a product. Replacements, removals and unused-brand deletion schedule unreferenced files for cleanup. Older brand callers that omit file fields preserve existing attachments. Brand saves retain existing permissions and optimistic locking.

Product pages show the active assigned brand's attachments above Questions, alongside product-specific documents, using the existing `show_documents` section setting. A single shared modal previews PDFs and images on demand; other supported formats offer a download link. All formats retain a new-tab fallback. Public file requests recheck product visibility, actual current brand ownership, active brand and ready-file state. Admin previews require `brands.view`. Private storage paths are never exposed; responses retain MIME, nosniff and no-store headers. Only successful PDF responses from the two public document routes allow SAMEORIGIN framing. PDFs use a deny-all web-content CSP with self-only frame ancestors; other formats keep CSP sandbox. Admin responses and all other routes retain frame denial. CSP sandbox cannot be used for PDFs because it [blocks Chromium's native PDF viewer](https://issues.chromium.org/issues/40754148). No document is fetched until opened.

Deploy with the normal migration, frontend build and worker/scheduler restart. The local Nike example has three explicitly labelled demo shoes and a shared sample PDF; the PDF is illustrative, not official Nike sizing information. Demo products and their category explicitly opt out of XML sitemap discovery.

Bestseller periods, minimum sales thresholds and category exclusions now follow [General → Catalog settings](general-settings.md#best-sellers); all-time remains the default. This supersedes fixed all-time descriptions below.

Catalog owns brands independently of descriptive product features. Catalog → Brands provides search, status filtering, sorting, pagination, localized name/description/alternative text, a private image, stable unique code and manual position. Names are required in every active language; descriptions are sanitized rich text. Inactive translations survive edits. Public names follow the configured default-language fallback, never an internal code.

`brands` and `brand_translations` follow the existing locale-linked relational conventions. A product has one optional `products.brand_id`, assigned in its existing General tab. Product filtering accepts a brand, duplication retains it, and older save payloads preserve the association when omitted. Variations are products and have their own brand association. Assigning a brand does not change pricing, stock, feature values or product publication.

This makes the dedicated brand association authoritative for brand blocks and rankings, refining A23/A61: existing Brand/MARKA feature values are preserved as descriptive legacy facts, with no automatic inference or synchronization. Other landing-page features retain their existing meaning. Merchants can migrate associations deliberately; editing a feature never silently changes the dedicated brand. The storefront product detail implementation and layout are unchanged by this delivery.

`brands.view` and `brands.manage` protect the admin boundary and mutations. Saves, status changes and deletion use the existing audit operation, catalog advisory lock, transaction and optimistic version. PostgreSQL checks codes/status/position, restricts deleting brands referenced by any product (including archived products), and cascades translations and layout selections when an unused brand is deleted. Disable a used brand to remove its merchandising blocks without altering products. Images reuse private MIME-validated JPEG/PNG/WebP uploads (5 MiB / 6000 px); detached originals follow the existing retention policy. Owner-checked public image streaming requires an active brand.

## Layout blocks

- **Brands**: ordered manual selection, all-time best-selling brands, or alphabetical brands. With Best sellers, an optional single brand picker switches the content to that brand’s best-selling products (for example Apple), using the shared product cards and brand heading. Product mode uses standard product card defaults and independent product image dimensions/per-row settings, so logo sizing cannot shrink product cards. Leaving the picker empty preserves ranked brand logos. Manual and alphabetical sources always show logos, even when a saved bestseller brand selection exists. Templates are a brand carousel or one brand filling its grid. It reuses category-block image sizing/radius, rows, per-row count, scrolling/navigation, background, responsive visibility, title typography and link settings. Only active brands with at least one currently eligible listing product appear. Missing pictures leave readable brand names.
- **Products by brand**: select one active brand, then use every existing Products block setting and its single-product/carousel templates. Sources are newest, all-time bestsellers, applicable sale, or ordered manual products. The manual selector searches name/SKU within that brand, and server validation rejects mismatched products. Changing the selected brand clears manual selections. Live resolution also checks ownership, so reassigning a product cannot leave it in the former brand's block. The heading uses the brand name/logo and optional localized block title; cards use the existing shared rendering and authoritative pricing pipeline.

Brand product headings use a prominent brand name/logo and an automatic localized Best sellers subtitle for that source. Both brand block types offer an opt-in paid advertisement flag (off by default), exposed as an Ad disclosure with a tooltip available on hover, keyboard focus and tap. This is merchant-declared placement metadata; it does not change ranking.

Both are registered `BlockType` implementations through `StorefrontRegistry`; there is no second layout editor or card settings definition. Normal layout inheritance, placement devices, widths, ordering, limits and versioned saves apply. Brand landing pages now use the dedicated brand code at the root (for example `/apple`) by default. Brand tiles link there only while this source is enabled and no existing route, saved page or root category owns that URL.

## All-time ranking and performance

Ranking measures **units sold**, using `ReportOrders::productUnitTotals()`: fully paid, positive-total orders, excluding void statuses (final and restoring stock). There is no date window. Unpaid/cancelled orders do not count; brands with zero qualifying sales do not appear in bestsellers. Brand totals sum the units of their currently publicly eligible products. Historical units follow the product's **current** brand association; this is merchandising attribution, not an immutable order-time brand report. Refund records do not exist, so refunds are not subtracted.

Queries use the existing public listing scope, including active category ancestry, customer-group access and configured availability visibility. Brand and product status changes take effect immediately. Newest/bestseller products across brand blocks use a partitioned SQL ranking query per source, rather than queries per brand/card. Cards, media and prices are batch loaded. Sale discovery uses the existing applicable pricing calculation in batches of 100, bounded per brand by the configured display limit; very large sparse-sale catalogs retain the existing scan limitation.

Only existing layout structure caching is used. Brand content, product associations, eligibility, prices and paid sales remain live; no ranking/price cache or invalidation jobs are added. The migration increments layout versions once to invalidate structures predating the normalized brand selection column. Public props exclude internal codes, audit information and sales totals.

## Landing-page source

General settings → Catalog → Brand landing pages selects the single public source. The default is dedicated brands, using their existing unique code; switching off enables active, complete `landing_pages` feature options at their localized slug (default-language fallback). These pages list their products like categories (A115, see [category listings](category-listings.md#brand-pages)): the shared Catalog landing layout holds the product filters beside the protected main content block, which shows the brand's image, name and description above the brand's products (a legacy option page lists the products holding that option). Brand product associations remain independent of legacy feature values.

Changing source requires both `settings.manage` and the separate `settings.brand-landing-pages` capability, plus an explicit SEO acknowledgement, enforced on the server. Permission synchronization registers the capability without granting ordinary roles; super admins inherit it. Other settings can still be saved without this capability when the source is unchanged. No automatic redirects or content conversion occurs. Existing metadata stays saved. In brand mode, selecting the feature landing purpose and editing its image/description/SEO fields are blocked; option labels and all variation configuration remain available. An unchanged legacy purpose may be retained while editing other settings. Existing explicit routes, saved static-page slugs and root-category slugs are reserved and never replaced by either source; brand carousel cards omit conflicting links. Changing a brand code changes its public URL, so plan redirects before renaming codes.

## Landing-page banners

The brand editor's Image tab has an independent banner upload, optional safe URL and locale-linked `banner_alt` input. `brands.banner_image_media_id` references the existing private `media_files` store (indexed FK, restricted deletion); `brands.banner_link` is nullable and `brand_translations.banner_alt` defaults to empty. The additive `2026_11_13_000200_add_brand_banners` migration preserves existing logo/text data and extends the reviewed audit fields with the banner media ID and alternative text. Banner URLs are excluded from audit snapshots.

`brands.manage` and the existing optimistic brand version protect saves. Existing callers that omit banner fields preserve them. Both uploads use actual PNG/JPEG/WebP decoding, the existing 5 MiB/6000 px limits and rollback cleanup; a failed second upload also cleans up the first upload's uncommitted bytes. Replaced/removed originals follow the established detached-media retention policy. Shared media maintenance checks both logo and banner references. `/admin/brands/{id}/banner-image` requires `brands.view`; public streaming rechecks active-brand ownership for either image.

The existing full-width Catalog landing **page heading** block shows the optional banner after the brand heading and above the filter/product row. The brand logo and its carousel presentation are unaffected. Banner images retain their natural ratio and fill the block width; a valid saved link wraps the picture in the same window, while an empty link leaves it a picture. Public URL validation runs again on output. Banner alt text falls back from the requested locale to the configured default language, then to the brand name. No banner is sent for legacy feature-option landing pages. Removing a banner hides its public image/link without removing the brand logo, products or stored link/alt settings.
