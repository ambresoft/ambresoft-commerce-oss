# Central audit ledger

Authorized by the comprehensive CMS audit request, 2026-10-10. Laravel MVC/Inertia, PostgreSQL and existing Redis sessions remain unchanged. No external collector, queue, API architecture or new UI library was introduced.

## Ownership and API

`App\Audit\Domain\Model\AuditEvent` is a plain typed payload. `AuditLogger::record()` accepts registered outcome actions and reviewed scalar metadata keys, validates outcome/entity identifiers, strips control characters and bounds text. Unsupported metadata keys/objects are discarded. Do not pass request bodies, arbitrary exception messages or credentials. Add a stable identifier to the registry and a persisted test before introducing an event. Infrastructure adapters call `AuditLogger::operation(entity, actorId, callable)` around business entrypoints: it establishes the explicit actor, restores the caller's context, logs failed/denied outcomes after the operation's transaction rolls back and avoids another HTTP failure event for the same failure.

`AuditContext` supplies a server-generated UUID correlation ID, source, optional actor email, role-slug snapshot, optional trusted request IP and optional user-agent. Request context runs after session initialization and before forgery/authentication/authorization checks. Client-supplied request IDs are ignored. Laravel's current configuration does not trust forwarded proxies; `X-Forwarded-For` is not accepted as a client IP. If deploying behind a proxy, explicitly review Laravel trusted-proxy configuration. Context is cleared/restored at request, command and job boundaries, including direct file-cleanup invocation. Direct database maintenance without context is `system`, never an unrelated logged-in user.

## Persisted mutation policy

Migration 001300 creates `audit_logs` and PostgreSQL capture functions/triggers. `AuditTables` inventories the reviewed fields. Only actual differences enter the ledger; timestamps, lock versions, catalog revision bookkeeping and cleanup-dispatch bookkeeping are excluded. A row write and its audit write share the same transaction, including Eloquent, query-builder, recursive category participant, import, bulk and internal-script paths. Additive migration 001400 consolidates each affected entity within the same server transaction and correlation ID: initial before values, final after values, and one mutation entry. Net unchanged scalar fields and delete/reinsert cycles disappear. Only still-uncommitted capture-trigger records can be consolidated; ordinary SQL updates remain blocked and committed records remain immutable. Historical rows receive no transaction backfill. Password and redacted-text markers preserve evidence of writes without retaining secret/text values; they cannot reconstruct a reverted secret or redacted body. No duplicate model observer or HTTP success logger is installed. Relationship/localization rows describe their own changes under the same request ID; these are distinct affected records, not repeated copies of the parent event.

## Security, privacy and failure policy

The ledger has no actor/entity foreign keys; string identities and safe snapshots survive deletion. PostgreSQL blocks row updates/deletes except the explicit expiry-pruning path. There are no HTTP mutation/delete/export endpoints for the ledger. `audit.view` gates both list and details and requires an active, verified persisted Super Admin role. Ordinary staff cannot gain access through permission grants, including legacy grants. Audit access is not offered or accepted in role permission editing. Successful audit-list/detail reads produce no audit event; denied attempts remain security events. Existing viewing records are preserved.

The field allowlist omits session/remember/reset/access tokens, credentials, storage keys and queue payloads. Password changes store only `[REDACTED]` markers, never hashes. Descriptions, merchant Text values and long fields use redacted character-count summaries; equal-length changes still generate a change entry because comparison occurs before summarization. Exact decimals and related IDs remain strings. JSON details are rendered with React escaping, never as HTML. Actor email/attempted login email and IP are privacy-sensitive snapshots: review lawful purpose/access/retention for your deployment. `AUDIT_ACTOR_EMAIL=false` disables actor/attempted-email snapshots (the separate, reviewed user email-change field still records account administration); `AUDIT_IP_ADDRESS=false` omits IP; user-agent is disabled unless explicitly enabled.

Successful data mutations fail closed when their audit insert fails and roll back. Explicit event insertion failures emit a minimal operational CRITICAL signal and throw `AuditWriteFailure`; failures are never silently swallowed. A failed login/registration response invalidates authentication state, and logout is logged only after logout/session invalidation/token regeneration complete. A database outage cannot persist a database security event: it must trigger operational monitoring and an unsuccessful request, not a fabricated audit row. No synchronous external call is made. SQL/filesystem/mail are not a distributed transaction: a notification or storage operation may already have happened before a later persistence failure. Existing idempotent file-cleanup retry/re-reference safeguards remain necessary.

If a caller deliberately wraps a supported business operation in an **additional outer transaction**, both its successful and failed audit records remain governed by that outer transaction. A rolled-back success disappears correctly; callers must record the final failure after their outer rollback. HTTP/import/job boundaries cover current production paths. Do not claim durable failure history for arbitrary third-party transaction wrappers or database-superuser actions.

## UI and performance

`/admin/audit-logs` and `/{id}` provide 30-row server pagination, bounded search (actor email/ID, entity ID/label, description), actor/action/entity/outcome/origin/request-ID filters, inclusive UTC date bounds and stable timestamp/ID ascending or descending order. Timestamps are stored as timestamptz and serialized as UTC ISO strings; the table displays browser-local time using the administrator's language. The list reuses the Products FilterBar/chips, sorting and data-table patterns, with a visible IP column. Localized activity labels distinguish editor openings from edits and system automation from unauthenticated visitors. Details show readable Before/After rows; raw identifiers and context are available in a collapsed technical section. Editor openings preserve a bounded entity-name snapshot and skip partial Inertia reloads used for selector searches. Loading, empty and field-error states reuse the admin design system. English/Greek labels are provided; other CMS UI languages explicitly fall back to English.

Indexes cover time/ID, actor/time, action/time, entity/time, status/time, request/time and entity identity/time. Contains search remains bounded-page PostgreSQL ILIKE (no claim of indexed substring search); measure real volumes before introducing a search index. The actor/role snapshot is reused within a context, with no entity graph eager loads. Multi-row configuration/order/import changes can produce many distinct records; this is deliberate durable field history. Inspect write overhead and ledger growth during production capacity testing.

## Deployment, retention and extension

Run `docker compose exec -T app php artisan migrate`, then `docker compose exec -T app php artisan cms:permissions-sync`; build with `pnpm build`, and restart long-lived workers after deploying providers/context changes. Both migrations 001300 and 001400 are required. No backfill or destructive catalog seed is run.

Retention is disabled by default: no job is scheduled and no records are automatically deleted. After approving a business/privacy/legal retention policy and backup plan, set a positive `AUDIT_RETENTION_DAYS` (1–36500) and explicitly run `php artisan cms:audit-prune`. This expires only older records transactionally and records the deletion count/policy; an audit-write failure rolls pruning back. The command is an operator action, not a CMS permission or user-facing delete feature. Never run it without a reviewed policy. Protect database backups, replicas, service credentials and diagnostic logs consistently; test restore and retain off-host backups. Database owners/superusers can disable triggers or truncate/drop tables: this protects normal application operations, not a compromised database administrator. Stronger forensic tamper evidence requires separately authorized immutable/off-host storage.

When extending the CMS, add reviewed table/field capture through an **additive migration** (never reinterpret archived history), update the coverage inventory and tests; call the shared logger for outcomes without persisted row changes. Keep operation/source/actor semantics explicit. Do not audit ledger tables themselves.

## Honest coverage limits

There is no inventory/stock/sale-price/customer/page/brand entity, MFA, invitation, impersonation, integration credential, discount, storefront or public API implementation to instrument. Brand/author landing variants are existing Feature option metadata and are covered. Redis TTL session expiration is not emitted by the current session handler, so an exact `session.expired` timestamp is not fabricated; session creation/logout and observed hash-based revocation are covered. No new session store or secret-bearing session identifier was added. Operational deployment/module configuration files and arbitrary shell/file changes are outside the database ledger; no runtime addon-installation workflow exists. Existing logs before deployment remain in their original stores. These limits preclude a claim of universal activity or external security certification.
