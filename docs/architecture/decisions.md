## Store model (A08)

| Choice       | Benefit                                                 | Cost                                                                                    |
| ------------ | ------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Single-store | Clear ownership, deployment and permissions; focused v1 | Future multi-store needs explicit scoping migrations                                    |
| Multi-store  | Shared catalog/operations across channels               | Must choose shared/store-local prices, stock, users, URLs, settings and permissions now |
| Multi-tenant | Independent merchants on hosted infrastructure          | Isolation, provisioning/routing, cache/queue/storage and operational guarantees         |

Choose single-store v1. Commercial distribution can mean separate installations, not SaaS tenancy or marketplace vendors. A future Store record describes the installation's trading identity, not a tenant. No universal store_id, global tenant scopes or default tenant-1 data.

Future multi-store remains possible through explicit ownership, centralized configuration, theme boundaries and relational joins. An approved migration can add store memberships/overrides, backfill records and scope uniqueness/authorization/cache keys. It is a migration project, not a flag. Multi-tenancy and vendor marketplaces are outside v1 scope and need separate design.

## Product/variation choice (A11–A12)

Choose dedicated variation records over CS-Cart's product-as-variation pattern. Product owns merchandising/categories; variation owns SKU/stock/base price. One default variation supports a simple product without nullable product-or-variant owners. Designated feature values identify variations; wrapping/engraving remain purchase options; option combinations express compatibility.

This avoids dual stock truth. Tradeoff: product editing coordinates its default variation, and overrides need explicit rules. Do not build a universal inheritance engine. Exact fields and sparse tuple generation remain open until catalog implementation.

## Simple product stock replaces warehousing (A67)

A67 (2026-10-11): The explicit Phase 7 specification cancels and archives the "Warehousing & Complex Inventory" plan and supersedes its decisions. Stock is a single non-negative integer `products.quantity` (default 0) on each product record; variations are products, so each has its own. `list_price` is an optional reference price (never auto-copied from price), `min_qty`/`max_qty`/`qty_step` are nullable (unset never restricts), and `out_of_stock_actions` is `N` (default: no purchase at zero stock) or `B` (backorders). `S` (notify) is not offered because no notification capability exists; adding it is an additive constraint change. Stock never alters product status or visibility. No warehouses, locations, ledger, reservations, thresholds, inventory permissions or connectors. Existing `products.*` permissions govern all changes. [Contract](products.md#simple-product-stock-phase-7).

A68 (2026-10-11): Settings → General introduces one installation-wide typed settings row (`general_settings`, id = 1 enforced by CHECK, optimistic `lock_version`, `updated_by`) guarded by the new `settings.manage` capability, which synchronization registers without granting. Its first option is the default out-of-stock action (`N` | `B`). A product's `out_of_stock_actions` becomes an optional override: NULL follows the general setting (the effective value is resolved at read time, so a change reaches every following product without rewriting product rows); `N`/`B` is a deliberate override even when equal to the current general value. Migration 001700 turns Phase 7 default `N` values into NULL, which preserves behavior because the general setting starts at `N`. New options are added as typed columns by later additive migrations; a key/value or JSONB blob is not introduced. Still no storefront or cart enforces the action. [Contract](general-settings.md).

A69 (2026-10-12): Phase 8 adds the `Tax` bounded context. Taxes are merchant-defined (no legal rates are hardcoded or seeded), each with locale-linked names, an integer priority (0–9999), active/disabled status, a price-included flag and a shipping/billing address basis. Rates live in `tax_rates`, unique per (tax, rate area), either a percentage stored as an exact `numeric(12,8)` fraction (0.24 = 24%, 0–100%) or a fixed `numeric(20,6)` amount in the primary currency. Rate areas are reusable, relational (countries, optional region codes, at most one default fallback area) and are owned by Tax now but written so shipping zones can reference them. Products reference taxes through `product_taxes` (primary key (product, tax), `RESTRICT` on the tax): deleting an assigned tax is refused and disabling is the retirement path. Matching: active areas with an explicit rate for the tax only; region > country > default, ties to the lowest area ID; an explicit 0% never falls back; a missing rate is reported (`no_rate`/`address_required`), never treated as zero. Calculation rules (priority groups, compounding, inclusive extraction, rounding once per tax half away from zero, exemption removing the included component) are documented in [taxes.md](taxes.md). No customer exemption field is added because no customer model exists; the calculation context carries an explicit `exempt` flag.

The add-on then queues a Measurement Protocol `purchase` for visitors gtag identified, reading the secret only when sending. Visitors without the cookie (blocked or never loaded) are not tracked server-side. Google's 2xx is final; a refusal is logged and never retried. Admin-created orders are not purchases. Consent remains the merchant's responsibility.

A149 (2026-11-10): The bundled, free `ambresoft/gdpr-cookies` add-on ("GDPR Cookies") is the storefront's consent manager. Its rules follow the EDPB cookie banner taskforce (2023), the Greek DPA recommendations 1/2020, CNIL and Google Consent Mode v2:

- **Banner:** the first layer offers "Accept all" and "Reject all" with the same size, font and colour, plus category settings. Categories are Necessary (always on), Preferences, Statistics and Marketing, none pre-ticked. The banner never blocks the store, and scrolling is not consent.
- **Storage:** the choice lives in the unencrypted first-party `cms_consent` cookie (`id.version.flags.time`) for 1–12 months (default 6). It is re-asked when the version changes, by "ask everyone again" or any script change.
- **Proof:** one row per decision (ID, version, choices, action, time; no IP or user agent) is kept for the consent period plus 12 months.
- **Withdrawal:** a persistent cookie button reopens the settings. Withdrawing deletes that category's declared cookies and reloads the page.
- **Content:** merchant text, category text and cookie declarations (provider, per-language purpose and duration) are locale-linked, with built-in wording as fallback. The CMS's own cookies are declared from the start.
- **Scripts:** staff with the separate `ambresoft.gdpr-cookies.scripts` capability (granted to nobody by default) may add vendor snippets to a category, as A128 allows only by this decision. Scripts run only after consent to that category and only on A147's public pages. Changes are audited, and private pages load fresh.
- **Core:** core owns the `consentManager` slot, the `cms_consent` reader (`StorefrontConsent`) and `resources/js/storefront/consent.ts`. While a consent manager is active, Google Analytics waits for Statistics and Google Tag Manager for Statistics or Marketing, using basic Consent Mode v2 (defaults denied, then the visitor's choice). Server-side GA purchases also require Statistics.
- **Not included:** the IAB TCF advertising tab, which requires IAB registration and CMP certification.
