# Language administration and strict content validation

This Categories/localization extension implements Settings → Languages, the separate sidebar Translations screen, and the personal language selector in the admin header. Phase 4 now adds the distinct [Product completeness policy](products.md): default-language name required, other-language content optional. The CMS remains a server-driven Laravel/Inertia modular monolith with pure Localization Application ports/handlers and Laravel persistence/dictionary adapters in Infrastructure.

## Supported pool and permissions

The shipped language pool is fixed for this release: English `en`, Greek `el`, Spanish `es`, French `fr`, Italian `it`, Dutch `nl`. `config/languages.php` is the trusted code allowlist; the existing relational `locales` table holds catalog activation/default settings. The additive 000500 migration adds four inactive reference rows and a UI-override table without changing existing en/el activation, default, preferences or category content. New installations still default to English. Do not add schema columns for languages. Expanding the shipped pool is a deliberate product/dictionary change, not arbitrary locale CRUD or a filesystem input.

`languages.manage` is the requested management capability, using the project's dotted permission convention rather than the illustrative `manage_languages`. Verified active staff need it for every settings/dictionary read/write; ordinary editors cannot change availability. Synchronization registers the definition without changing existing role grants. Assign it deliberately through Roles; the existing registered-capability Super Admin bypass applies. Personal language selection needs only normal staff access and changes that user's preference alone.

## Active catalog versus personal interface language

At least one catalog language must remain active and exactly one active default is required. Settings are saved atomically under the category advisory transaction lock, also used by catalog writes/imports. Reject unsupported, duplicate, empty or inactive-default selections. Deactivation retains translations and user preferences; it never deletes language rows or content. Activation/default changes invalidate CSV catalog fingerprints. Concurrent catalog saves cannot validate one active set and commit against another.

UI request locale = active user's preferred locale → active system default → English safety fallback. Header, account preference and translation-dictionary selectors list only the active languages saved in Settings → Languages; `PATCH /admin/locale` and dictionary filtering reject inactive codes. Guests use the system default. Deactivation retains a previously saved preference ID but displays the active default until the language is reactivated. Users can still choose independently from the active set without changing another user's preference. Shared `i18n.locales` supplies that same active set to admin language menus and catalog forms. The Settings activation checklist still shows all six shipped languages so administrators can enable another one.

## Strict catalog validation

With two or more active catalog languages, the localized category name, SEO/page title, SEO/meta description, slug, image alternative text and meta keywords are mandatory in **every active language**. The authorized fixes keep category descriptions and age warning text optional in every language, whether age verification is enabled or disabled; it must not block an unrelated image upload. Age-limit validation remains separate and requires a positive limit when verification is enabled. Normal slug derivation remains supported. Whitespace-only values fail. No automatic copying between languages is allowed.

With one active catalog language, forms show only that language. Its name and normalized slug remain required; other existing fields retain their single-language optional semantics. Non-translatable status/position/age/media validations are unchanged.

Validate the **resulting exact-row content**, not only submitted tabs. A complete untouched Greek row satisfies an English-only editor patch and remains byte-for-byte unchanged; a missing Greek row cannot pass by being omitted. Existing incomplete categories are retained, but normal editor saves/core-only changes must first complete them. Activation does not translate old data. No storefront exists: future publication/navigation must check current completeness before making coverage guarantees; do not mistake read-side fallback for complete translated content.

CategoryInput owns shared field rules and editor completeness rules. The editor and importer use the same transactional persistence operation with explicit validation policies. Only the category import entry point permits incomplete category translations, and that entry point independently requires categories.import plus the applicable create/update capability. Browser form input cannot select the import policy. ProductInput now implements the separately authorized Product-specific rules; it does not weaken Category validation.

CSV imports accept any subset of active languages, even one nondefault language when three or more are active. A new category needs a name in at least one active language; its slug can derive from that name. Missing languages remain absent translation rows (empty editor tabs), never copies or blank rows with fabricated identifiers. Updates preserve omitted columns and languages. Optional supplied text can be cleared in any language mode. Inactive-language headers are errors even when their cells are empty. Preview and confirmation enforce the same policy and reject stale locale settings. Missing path parents can be created disabled with default-language names in any language mode. Imported translations can later be added by ID-based CSV updates or completed through the strict editor. [CSV contract](category-import.md).

## Editable UI dictionary

Laravel keyed PHP dictionaries remain authoritative shipped defaults, using `lang/{locale}/{group}.php`, including namespaced module resources. Actual CMS UI groups (authentication, shell, staff, roles, permissions, categories, imports, language settings) ship keyed strings in all six languages; no independent React dictionary or hardcoded English UI is introduced. Existing Laravel fallback remains for unused vendor validation rules and stock email template prose. Translation parity/placeholder tests cover the current CMS dictionaries; native-speaker terminology review remains advisable before commercial release.

`ui_translation_overrides` stores locale FK, trusted namespace, group, key, text value, modifying user FK and UTC timestamps; a composite unique constraint prevents duplicate identities. It stores only **application wording overrides**, never product/category translations. Foreign keys retain locale integrity. A Laravel Loader decorator merges the selected language's overrides over its file resources, preserving normal namespace handling, fallback and literal dotted validation attribute keys. Both server `__()` and Inertia shared strings use this one dictionary. Queue/console translation calls use it too once the schema exists; installation can load file strings before migration.

Dictionary UI searches exact keys or text, filters one language and paginates 25 strings. Authorized users can edit any shipped core dictionary key, server validation key or enabled module's explicitly registered UI group. Unknown keys/namespaces are rejected, never used as arbitrary filesystem paths. Preserve the exact named placeholders from the original English string; nonempty bounded text only. React renders text escaped, not as HTML. Restore deletes only the customization, exposing original shipped wording again. Source files are never changed by the editor. Editing is last-write-wins per string; collaborative version/history workflows are not implemented.

Only current-locale/fallback groups and overlays are loaded for requests; the dictionary editor reads one requested locale plus English defaults, not all six dictionaries. Overrides need no deployment cache flush because ordinary HTTP requests reload the Laravel dictionary. Long-lived workers must restart after code/dictionary deployments; no new worker platform is introduced. Logs record actor/locale/key or active/default changes, never translated content. These are operational logs, not a durable audit ledger.

## Security and verification

Session, CSRF, verified/active staff gates and server capabilities remain enforced. Language setup uses explicit allowlists and transactional defaults; overrides allow only trusted registered keys, bound SQL, bounded values and original placeholder sets. User input cannot activate arbitrary locale directories, change another user's preference or grant capabilities. Merchant translations keep normalized category-owned rows and their uniqueness rules. Uncategorized remains immutable, UI-localized and exempt from merchant completeness.

The original language-extension tests cover permissions, six-language pool, safe defaults/activation/deactivation, active-only admin selectors and server preference validation, retained preference fallback/reactivation, Greek-only editing, every required Category field in both active locales, direct-handler enforcement, unchanged translations, incomplete legacy records, partial CSV imports and later completion, inactive-language headers and stale language sets, override search/edit/restore/placeholders, server/browser/module parity, wildcard validation keys, migration preservation and existing authentication/RBAC/categories. Frontend interactions cover explicit settings submission, exact-key edits/restoration and selection from active languages. Phase 4 adds separate Product tests for optional non-default content and safe eligibility changes; storefront remains absent.

Current local verification: 148 backend tests / 10,055 assertions and 27 frontend tests pass, together with static analysis, types, lint/format and the production build. The active-only selector regression tests cover the header, account and translation dictionary; the Settings activation checklist still offers all six shipped languages. The additive migration is applied locally; rollback tests use only cms_test.
