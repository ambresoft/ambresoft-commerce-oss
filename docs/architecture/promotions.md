# Automatic promotions and existing coupons

Marketing → Promotions extends the existing Marketing context. Laravel 13, PostgreSQL, Inertia 3, React/TypeScript and the current admin components remain in use. Promotions run in the real order quotation, creation and repricing pipeline, including trusted internal `source=checkout` callers. The storefront cart now uses that same quotation pipeline on every calculation, with server-derived customer identity, buyable products and saved quantities. Checkout/order placement remains separate; browser inputs cannot supply prices, customer IDs or group memberships.

The behavioral reference is [CS-Cart's promotion setup](https://docs.cs-cart.com/4.17.x/user_guide/manage_products/promotions/setting_promotion.html): explicit conditions, benefits, scheduling, priority and stopping later rules. Ambre's implementation, schema, rounding and lifecycle are its own. No CS-Cart code or schema was copied.

## Existing Coupons architecture and integration

`Coupons` validates/persists definitions and targets, authorizes direct writes, applies optimistic versions and archives deleted definitions. `CouponQueries` supplies the unchanged list/editor/history. `CouponPricing` validates the case-sensitive code, enabled/archive state, inclusive store-date boundaries, minimum, registered-customer requirement, product/category scope and remaining allowance. `CouponAmounts` supplies exact percentage/fixed arithmetic. `OrderPricing` allocates discounts before calling the existing tax service. `CouponRedemptions` maintains the existing redemption ledger inside order transactions; a PostgreSQL capacity trigger and active-order unique index protect concurrency.

Standalone coupons need no promotion record. A coupon named `test` with code `test123` and amount `10%` continues to discount €100 by €10. Current coupon codes, names, settings, dates, targets, archived records and redemption history are neither moved nor rewritten. Coupon administration stays unchanged.

A coupon-based promotion references **one existing coupon**, with at most one wrapper per coupon. The coupon remains the source of its monetary benefit, product scope, shipping benefit, dates and usage limits. The promotion adds flat conditions, its own schedule/status and priority. Coupon restrictions are always validated first; failing wrapper conditions or schedule returns a coupon-field validation error. Disabling a wrapper prevents that coupon from being applied; it does not silently fall back to a standalone coupon. Benefits and codes are edited in Coupons, not duplicated in Promotions. To grant a distinct additional benefit, configure an automatic promotion with the appropriate conditions.

The validated coupon benefit enters calculation once. A standalone coupon keeps its established first position after product sales. A linked coupon participates at its promotion priority, using the existing configured discount against the remaining eligible merchandise. If stopped before granting any benefit it is not redeemed. Coupon redemption monetary snapshots use dedicated coupon-only amounts, so concurrent automatic benefits never inflate coupon history or create a competing usage counter. Coupons remain limited to one entered code per order.

## Administration, conditions and benefits

The list supports search by localized name/code, status/mode/benefit filters, stable sorting, 25/50/100 pagination, enable/disable with optimistic versions, scheduled/active/expired/disabled indicators, dates, priority and usage. Coupon-mode usage/limits come directly from the existing coupon ledger; automatic usage counts current, unreleased order snapshots. `promotions.view` and `promotions.manage` protect reads and mutations. Ordinary permission sync registers them without granting existing custom roles. UI dictionaries cover all six supported languages. Merchant names/descriptions have locale-linked `promotion_translations`; names are required in every active content language and omitted inactive translations are retained.

Each promotion has up to six flat conditions, at most one per type, combined by AND or OR. No conditions means unrestricted. Supported rules:

- Inclusive minimum, maximum or range of merchandise subtotal.
- Any or all selected products present. This selection is separate from which products receive a discount.
- Products from any selected category, including active descendant categories through active hierarchy paths.
- Minimum total cart quantity, or quantity of independently selected products/categories. Unrelated items never satisfy targeted quantities.
- Any selected active customer-group membership; multiple memberships are a union. Guests do not inherit group restrictions, including a default group. Unrestricted promotions allow guests.
- An active selected shipping-method ID with an available server quote. Changing the method changes the match.

Automatic benefits are percentage (positive, at most 100), fixed positive primary-currency amount, or free shipping. Monetary benefits can target the order merchandise or product lines. Product-line targets are all products or a product/category union, with optional product/category exclusions and an option to skip active product sales. Parent category targets and exclusions include active descendants.

Targets use relational tables and foreign keys. Deleting a target retains a null tombstone. A deleted required product cannot satisfy an all-products condition. A deleted benefit/exclusion target makes that automatic promotion fail closed until repaired; an empty restricted selection never becomes all products. Disabled referenced groups/categories/products/shipping methods cannot satisfy their positive conditions. Editors retain a visible missing-selection marker and require valid references on save.

## Exact calculation order

1. Read authoritative original product/order inputs. `ProductSales::price` retains its existing group, date, quantity, priority and stock-capacity behavior. Product sales are not rewritten.
2. Freeze the eligibility subtotal after product-sale pricing, removing included tax calculated by the existing tax service. This basis excludes coupons, promotion discounts, shipping and added tax. Every promotion uses this same basis, so it cannot qualify or disqualify itself through its discount.
3. Apply an entered standalone coupon at its legacy position, if present. Evaluate automatic/linked promotions by ascending numeric priority, then ascending promotion ID. Equal priorities therefore follow creation order.
4. Order-level percentages compound on remaining eligible entered merchandise prices; fixed amounts are capped and allocated across that remaining value. For example two 20% order discounts on €100 give €36 combined, not €40. Linked coupons use their configured percentage/fixed amount at their priority. These prices may include tax, matching existing coupon semantics; a 20% discount on a €124 VAT-inclusive price is €24.80, and tax is then recalculated.
5. A product-line promotion calculates its candidate against the original product price, compares the resulting price with the actually active product sale and grants only an improvement. It never multiplies the product-sale price by another product-line discount. If it wins, the line returns to its original price and records the full allocated promotion discount; the losing product sale is not reserved. The first successful product-line promotion by priority claims that line. Later product-line promotions can benefit other lines. Fixed product benefits are distributed over their eligible target basis before comparison, so a better existing sale may leave part of that fixed offer unused. Earlier order-discount allocations remain fixed if a later product-line offer wins; later order discounts use the new remaining amounts. All allocations are capped so a line cannot become negative.
6. Free shipping requires an existing eligible, available server quote. Automatic free shipping waives the quoted transport component, leaving per-product freight and carrier surcharges intact. It does not fabricate an available method or waive unrelated payments/fees. Taxes are recalculated on any remaining shipping charge. Legacy coupon free shipping still removes the entire shipping charge according to the existing coupon contract. Combined shipping benefits are capped at the original charge.
7. Recalculate product and shipping taxes through the existing tax pipeline. Use existing decimal/BCMath operations, currency precision, half-away-from-zero rounding, largest-remainder allocations and at most two unit-price fragments for indivisible line remainders. Total equals merchandise subtotal minus discounts plus added tax plus remaining shipping.

Each promotion grants at most once per calculation. Stop other promotions takes effect only after a positive merchandise or shipping benefit and stops **strictly lower** priorities; equal-priority promotions still run. No-benefit matches do not stop later promotions. Product-price benefits and shipping benefits can coexist. Existing standalone coupons are not retroactively stopped by automatic promotions.

Every quote starts from original inputs. `order_items.pricing_basis` preserves the original unit/base price and sale identity for explicit order repricing; stored already-discounted totals are never subtracted again. No-op historical edits and status/payment events retain contracted totals. Changing quantities, products, customer, coupon, tax-relevant address or shipping in a new calculation re-evaluates current rules. The order editor hides an old quote when its input values change and displays per-promotion merchandise/shipping benefits; the saved order displays snapshot names/amounts.

## Scheduling and currency

Optional editor datetimes use the configured store timezone; database timestamps are UTC. The interval is `[starts_at, ends_at)`: start included, end excluded, and end must be later than start. Empty bounds are indefinite. Eligibility checks run on server time during each quotation/creation/repricing; no scheduler or delayed activation state is introduced.

Fixed amounts and subtotal bounds are denominated in the primary currency. Existing primary-currency conversion also converts these definitions and advances promotion versions, while historical order/snapshot currencies and amounts stay unchanged. Precision reductions reject lossy values; conversion rejects a fixed benefit that would round to zero and validates overflow through the existing conversion rules.

## Orders, usage and repeat submissions

`OrderAdministration::create` recalculates under the existing catalog/product/coupon transaction locks before inserting an order. `order_promotions` snapshots the granted promotion ID/name, associated coupon code, benefit type, exact merchandise/shipping amounts, per-order-item allocations, currency/precision and timestamps. A unique `(order_id, promotion_id)` key prevents duplicate application rows. `is_current` distinguishes explicitly removed benefits from current ones; repricing can replace current snapshots while ordinary no-op saves and later definition edits cannot change historical totals.

Cart/order previews never redeem anything. Saved orders reserve coupon usage at creation, **not payment capture**, following the existing business lifecycle. Restore-stock/cancel statuses release coupon allowance and promotion usage, retaining financial history. Reopening reacquires the existing coupon capacity and marks current promotion snapshots active without repricing expired definitions. Repeating the same status event is a no-op. Failed payment attempts do not themselves release usage; cancellation follows the existing order status path. Refund processing does not exist in this repository, so no new refund accounting is invented. Automatic promotions have no independently configured redemption quotas; new quota semantics were optional and have not been added.

The cart evaluates automatic promotions even when no coupon is entered or the code-entry setting is disabled. Its summary shows each granted automatic promotion's localized name and tax-inclusive savings, separately from the entered coupon and gift-card payment. Coupon-linked promotions appear only in the coupon row. Quantity changes, reloads, schedules and current eligibility are reevaluated from original catalog inputs; no benefit is subtracted twice. Invalid coupons retain their explanation while eligible automatic offers still apply. The existing tax service projects before/after prices at currency precision, and per-line savings attribution reconciles coupon/promotion rows to the exact grand total even with mixed rates and subtotal rounding. Gift cards pay the resulting balance without changing their stored balance or redeeming anything. Shipping-dependent benefits require an actual shipping quote and are not invented on the cart.

Trusted checkout callers may supply a UUID `submission_key`. It is scoped to customer identity/normalized guest email and paired with a validated-input fingerprint. Identical repeats return the original order, without re-reserving stock, coupons or promotions; reuse with changed inputs fails. The transaction advisory lock plus a database unique key serializes races. Public browser retries cannot benefit from this until an actual storefront entry point passes a stable submission key; the existing internal API remains backward compatible for callers without one.

## Migration and deployment

`2026_10_25_000100_create_promotions` adds promotion definitions/translations, typed flat conditions, normalized targets and order application snapshots. Existing Coupons tables/rows are not changed. Additive order columns separate coupon-only discount amounts from combined discounts; existing coupon orders are backfilled from their existing totals. The new nullable item pricing basis and checkout submission keys preserve existing orders without inventing historical promotion records.

Apply `php artisan migrate`, run ordinary `php artisan cms:permissions-sync`, assign `promotions.view/manage` deliberately, and run `pnpm build`. Hard-refresh the admin. The running local app uses the `cms-foundation` Compose project even though the current shell defaults to another project; deployment commands must target the app/database actually serving the merchant. Do not start a second app/database or remove a volume to resolve a project-name mismatch.

Rollback is allowed before any promotion order snapshot exists; it removes only the additive structures. After use, rollback requires a database backup because dropping financial allocations cannot reconstruct the original tax contract. The migration refuses that destructive rollback. Database backup/restore remains the recovery path.
