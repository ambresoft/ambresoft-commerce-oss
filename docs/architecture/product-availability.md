# Product availability labels (A84)

Catalog owns merchant-editable availability statuses. These are customer-facing text labels, distinct from product lifecycle visibility and from stock quantities or purchase rules. A product, including each variation, has independent nullable `in_stock_status_id` and `out_of_stock_status_id` references. Null inherits the corresponding store default. Duplication copies the selections; legacy saves that omit these fields preserve them.

The product editor exposes both selectors in Pricing & stock → Stock (the second tab). It shows the saved resolved label and a management shortcut. Products → Availability statuses provides adding, renaming in every active content language, ordering, assigning defaults and deleting with an optional replacement. The UI uses the established dashboard controls and layout. English/Greek admin text is localized; the other supported admin languages currently use the English fallback. Initial merchant labels have translations in all six supported content languages.

`AvailabilityRules::bucket` chooses the in-stock label for positive quantity when inventory tracking is enabled, otherwise the out-of-stock label. When tracking is disabled, it chooses the in-stock label. `ProductAvailability::forProduct` resolves an override or store default and the current locale, falling back to the system-default content language. It is consumed by the admin's saved-label projection and is available to the later storefront product renderer. This change adds no public product page or theme. Labels do not alter quantity, available-from dates, lifecycle status, order stock movements or the existing out-of-stock purchase action.

Migration `2026_10_15_000800_add_product_availability_statuses` creates status and locale-linked name tables, and two indexed restrictive product foreign keys. The six editable starting labels are Immediately available, Awaiting supplier, Available in 1–3 days, Available in 4–6 days, Unavailable and Pre-order. Defaults start as Immediately available / Unavailable. Existing product quantities and purchase rules are preserved; all existing products initially inherit these defaults.

Each status has an optimistic version and nonnegative position. Names are plain text, required in every active language, at most 250 characters, with control characters rejected. Inactive saved translations remain intact. Unique partial indexes allow at most one default for each stock condition. Supported mutations preserve at least one default per condition; one status may serve both. To switch a default, designate another status as default. The current default cannot simply be unchecked.

Status mutation, product saves and reference replacement serialize under the existing Catalog transaction lock. Deleting an explicitly referenced status or a default requires a different existing replacement. Product references, including trashed products, and default flags transfer atomically before deletion. Affected product versions increment once even if both references used the deleted status; old product editors become stale. Replacement status versions increment too. An unused non-default status can be deleted without replacement. PostgreSQL independently restricts direct deletion of referenced statuses. All status/name/reference mutations are captured in the central audit ledger.

`availability-statuses.manage` protects management pages and writes. Product assignment uses existing `products.update`; product editors can read the selectable names without receiving management authority. Ordinary permission synchronization adds the definition without widening role grants. Status count is bounded to 1,000 through the supported write service.

Apply migrations, run `cms:permissions-sync`, assign the new capability where needed and rebuild the frontend. Tests cover defaults, multilingual completeness, localization fallback, product save/duplication, zero stock, tracking disabled, replacement/versions, legacy preservation, restrictive foreign keys and independent capabilities. Existing product and migration regressions and the product editor's selection/submission behavior are also checked.
