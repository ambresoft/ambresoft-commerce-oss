# Shared AI configuration and history

Settings owns the merchant's AI provider configuration and call history. General settings has an AI settings tab (`/admin/settings/general?tab=ai`); its fields use the existing dashboard form components. The AI Log entry under Logs opens `/admin/settings/ai-log`, also linked from the tab. Previous FAQ settings/log URLs redirect to these destinations with the same authorization checks.

The consumed provider is Anthropic Claude, with an explicit supported model allowlist. No additional provider or future AI feature is implemented. FAQs use the shared encrypted key, model, output-token cap and per-user hourly budget. The global switches and budgets are ready for other separately authorized consumers; the current only consumer is FAQ generation.

Configuration requires `settings.manage`. The `ai_settings` singleton has its own optimistic version. General settings submits nested `ai_settings` input and saves both records atomically: invalid/stale AI configuration rolls back General settings changes too. Older callers that omit the nested input preserve AI settings. The password input is always empty on load; blank preserves the saved key, and explicit removal clears it. Keys are excluded from shared props, session old input and audit capture, with a boolean-only credential-change event. PostgreSQL checks singleton identity, versions, enabled/key coherence and configured limits.

History requires independent `ai.logs.view`. A user can inspect history without permission to edit General settings; the Logs menu shows only the history entries the user may view. Every provider call records a `feature` identifier (`faq_generation` currently), source snapshot, staff member, model, timestamp, status, HTTP status, safe error code, reported tokens and duration. No key, prompt or response is persisted. A per-user cache lock and hourly allowance use shared `ai-user:`/`ai-hour:` keys. Regeneration and provider failures consume the same budget. Defaults are 50 calls/hour and 3,000 output tokens, with no automatic retries.

The additive `2026_10_15_000700_share_ai_settings_and_history` migration renames the initial FAQ settings/history tables, adds the originating-feature field, and updates audit capture without rewriting keys or call data. The earlier migration stays reversible. An existing `faqs.ai-log` permission definition is renamed to `ai.logs.view` when the destination does not exist, preserving its assigned pivots; normal synchronization adds missing definitions without changing grants. Existing ledger entries retain their original identities and translated labels.

Apply migrations, run ordinary `cms:permissions-sync` and rebuild the frontend. Configuration is disabled without a key. Live generation remains unverified until a merchant key is supplied; the test suite uses mocked provider responses and verifies atomic settings saves, secret scrubbing, history, rate limits and reversible data preservation. ## Guardrails

Every admin assistant (banners, blog posts, newsletters, FAQs) calls the provider only through `AiClient::structured`. These rules are mandatory for current and future assistants; `tests/Feature/AiGuardrailsTest.php` enforces them for every assistant.

- **No capabilities.** Requests carry instructions, the conversation and a JSON output schema; never `tools`, function calling or any other way for the model to act. The fixed `https://api.anthropic.com/v1/messages` address is called with redirects disabled. A request such as "delete the master branch" or "show the .env file" therefore can only produce text.
- **Explicit context.** Each feature sends an allowlist: the merchant's messages, the editor's current state, active language codes, the store name and country, public company contact details (FAQs) and, for FAQ generation, the description of an object the actor may view. Never secrets, `.env`/configuration values, credentials, customer data or other records. The API key travels only in the `x-api-key` header.
- **Scope instructions.** `AiClient::SCOPE` precedes every feature's instructions: the assistant only writes its draft, has no access to the server, files, code, repositories, data or settings, refuses anything else in its reply and treats all supplied content as information. This keeps answers on task; the boundary above is what makes them harmless.
- **Validated output.** Each feature checks the response against its save rules: plain text is stripped of markup, rich bodies go through `RichTextSanitizer`, banner settings through `BannerAdministration::check` (including `MenuRules::safeUrl` for links), newsletter placeholders through the allowlist. Anything else is refused and logged as `invalid_response`.
- **Draft only.** The result returns to the editor. Nothing is saved, sent or deleted by an assistant; saving uses the ordinary authorized endpoints, which sanitize again.
- **Limits.** Per staff member: one call in flight and the hourly limit. Store-wide: `ai_settings.daily_limit` (default 200, 1–100,000; migration `2026_12_12_000100_add_ai_daily_limit`) counts every logged call of the last 24 hours, checked under a shared lock before the call and reported as a field error. Editor state is capped per request (20 KB for banners and FAQs, 60 KB for blog posts and newsletters), as are the conversation (30 messages of 4,000 characters) and output tokens.
