# Project-wide instructions

- Build a premium open-source ecommerce CMS licensed AGPL-3.0-only (A161). Keep the root LICENSE unchanged; separately distributed add-ons may carry their own license. Never copy CS-Cart proprietary code or schema.
- Work only on the authorized phase and deliverables. The roadmap is context, not authorization. Phase 0 establishes architecture and a runnable foundation; authentication and the admin shell require separate Phase 1 authorization. Do not create future ecommerce placeholders.
- Follow the preferred direction: Laravel 13 / PHP 8.3+, PostgreSQL, Redis, Inertia, React, TypeScript, Tailwind, Docker, PHPUnit/Pest and Vitest where appropriate. Keep a modular monolith with Laravel MVC, server-driven workflows and admin-first delivery.
- Apply [context-first DDD](docs/architecture/layered-ddd.md) (A29): app/{Context}/Domain, Application, Infrastructure, Presentation. Keep Domain and Application framework-free; put Eloquent records/mappers and Laravel adapters in Infrastructure. Use PascalCase PHP directories, singular Model/Repository/Command/Query/Service categories and HTTP Controllers/Requests. Admin is presentation, not a business domain; Core means essential ownership, not a namespace. Create only consumed types/directories.
- Keep business rules on the server, relational integrity in PostgreSQL, and optional addons outside core. Preserve separate domain meanings for features, options, combinations and variations.
- Enforce persisted staff capabilities on the server. Use keyed Laravel UI translations; keep merchant text in entity-specific locale-linked translations, never language-specific columns. Read [authorization](docs/architecture/authorization.md), [localization](docs/architecture/localization.md) and the current [language/content validation policy](docs/architecture/language-management.md). Offer only active languages for admin UI preferences; preserve saved preferences with a default fallback when a language is deactivated. Share server field rules; keep strict editor completeness separate from explicitly permitted partial CSV imports. Reject inactive import-language columns.
- Do not introduce microservices, API-first architecture, a core visual page builder, blanket repository layers, CQRS or DDD ceremony without a concrete authorized need.
- Read [architecture overview](docs/architecture/overview.md) and [decision register](docs/architecture/decisions.md) before architectural changes. Distinguish accepted direction, proposals and open decisions; do not silently promote a proposal into a requirement.
- Use the relevant project skills under `.agents/skills/`: `ecommerce-architecture` for boundaries; `ecommerce-domain` for business semantics; `ecommerce-modules` for extensions; `ecommerce-database` for persistence; `ecommerce-admin` for admin UI; `ecommerce-development` for implementation workflow. Load only references relevant to the task.
- Also use relevant supporting skills under [`.agents/skills/`](.agents/skills/): `infer-conventions` for existing patterns; `laravel-best-practices` for Laravel implementation; `testing-best-practices` for tests; `inertia-react-development` for Inertia/React; `tailwindcss-development` for Tailwind; `security-audit` for security reviews. Read the selected `SKILL.md` before applying it. These skills supplement the project-specific skills; this file, the project architecture and the authorized task scope take precedence over generic examples. Do not load unrelated skills or infer authorization for additional work from them.
- `.agents/skills/` is the canonical shared library for Codex and Claude Code. `.claude/skills/` contains relative per-skill symlinks to it. Edit skill files in the canonical location; keep tool-specific settings and instruction entry points in their native locations.
- Every project skill created, imported or updated must work with both Codex and Claude Code. Keep one actual directory at `.agents/skills/<name>/` and a relative `.claude/skills/<name>` symlink; never maintain independent copies. Keep shared instructions tool-neutral where possible, preserve equivalent invocation restrictions through each tool's supported metadata, and verify frontmatter, links, references and scripts through both discovery paths before marking the skill work complete.
- Admin headers must use the shared `EditorHeader` pattern. Every admin and addon entity editor must place its editable status in the header using `EditorStatusSelect`: a compact colored pill with an accessible label and no separate visible “Status” label. Do not add duplicate status dropdowns or radio groups in editor bodies. Products, Categories and Brands are the reference implementations. Preserve each entity's permissions, allowed statuses, lifecycle confirmations and validation errors; list filters and dedicated workflow actions keep their own semantics. Keep Delete/Trash in the header's three-dot menu. See [shared editor tabs and actions](docs/architecture/admin-architecture.md#shared-editor-tabs-and-actions).
- Admin UI must reuse the shared design system before introducing a page-specific pattern. Put New/Create/Add actions in `EditorHeader.actions` at the right with a plus icon, never under the title or in `description`. Back navigation is the shared small borderless link below breadcrumbs and above the header, always labelled with `common.back` (Back / Πίσω), never Cancel or an entity name. Row names link to the same destination as their Edit action with the same permission guard. Use the Orders card pattern for detail sections. Show one editable status pill; put distinct computed storefront state below the title in metadata and put status explanations in `HelpPopover`. Merchant translation forms use `ContentLanguageSelector` and show the selected locale while preserving all drafts and locale errors; multilingual comparison tables are intentional exceptions. Customer account invitations require `ConfirmDialog` explaining the recipient, email and storefront-account access before sending; they never grant staff access. Keep these conventions across core admin and addon screens.
- All admin CSV import upload screens must reuse `resources/js/components/admin/CsvImportUpload.tsx` (`CsvImportUpload`, `CsvImportSteps`, `CsvImportInstructions`). Categories and Regions are the reference implementations. Keep the shared drop zone, selected-file details/removal, server-configured file limit, settings card, explicit preview action, progress and collapsed instructions; retain feature-specific validation, previews and confirmation on the server. See [the default CSV import UI](docs/architecture/admin-architecture.md#default-csv-import-ui).
- Inspect existing work before editing, preserve unrelated changes, and verify changes in proportion to their risk. Prioritize correctness, maintainability, extensibility, database integrity, security, performance, developer experience, then UI polish.
- Run checks in `docs/development.md`; follow `docs/architecture/security.md`. Keep secrets out of version control and authorization on the server. Never use floating point for authoritative money.

- For storefront layout work, follow the CS-Cart container → 16-column grid → block organization. Grids control independent side-by-side columns; each block fills its assigned grid. Use an Add block dialog with Create new / Use existing tabs and explicit single-item versus carousel templates. A single item fills the grid; a banner carousel shows one full-width banner per slide. Share the existing banner composition renderer between the admin preview and storefront so saved backgrounds, text, masks, buttons and device overrides stay visually consistent. Reuse the Order Statuses native drag grip and arrow-key interaction. Apply the same registered presentation pattern to future content types; adding a content type does not authorize building an otherwise deferred business module.

- All admin and addon form/detail sections must reuse `resources/js/components/admin/AdminCard.tsx` (or the shared form `Section` adapter). Use its divided heading, green icon tile, action slot and consistent padding; do not create a separate card design per page. Preserve compact item tiles, alerts, list tables and specialized canvases as their own controls.
